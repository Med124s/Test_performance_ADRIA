3. Moteur d’exécution

Moteur kaykhdem dakhel nfs JVM dyal backend : ma kaynch outil externe (JMeter/Gatling). Kol utilisateur virtuel (VU) kaykhdem f thread virtuel dyal Java 21 (Executors.newVirtualThreadPerTaskExecutor() f ExecutorConfig).

POST /api/executions {scenarioId}
  │ ExecutionTransactionHelper.prepareAndStart   (transaction courte)
  │   • refus si scénario/application archivé, ou 0 étape
  │   • Execution QUEUED + copie des paramètres de charge
  │   • copie de l'authentification de l'application
  ▼ réponse 202 immédiate ; la suite est asynchrone
HttpClientExecutionEngine.execute(steps, baseUrl, auth, loadSpec, handle, csvRows)
  │ 1. authentification résolue UNE fois (login réel si « connexion auto »)
  │ 2. VU 1..N démarrés avec un décalage = rampUp / N
  │ 3. chaque VU : itérations jusqu'à durée / nombre d'itérations / annulation
  │      étape → requête HTTP → StepOutcome (code, temps, succès, erreur)
  │      une étape en échec arrête l'itération en cours de ce VU
  ▼
finalizeExecution : ExecutionStepResult (+ copie de l'étape), statut SUCCESS/FAILED/CANCELLED
MetricGenerationService : une Metric par résultat (temps, code, débit, taux d'erreur)
AspectComportement réel
Utilisateurs virtuelsN threads virtuels ; décalage de démarrage rampUpSeconds × 1000 / N ms ; variables CSV distribuées de façon cyclique (une ligne par VU).
Fin du testDurée (durationSeconds), nombre d’itérations, annulation, ou 1 seul passage si aucun des deux.
Débit ciblePacingGate partagé par tous les VU (pas un par VU).
Succès d’une étapeCode = code attendu, sinon 200–399 ; plus l’assertion « la réponse contient » si configurée.
Timeouts10 s par défaut (EXECUTION_TIMEOUT_SECONDS), surchargeable par étape. Client HTTP/1.1.
AuthentificationBearer / clé API (en-tête ou paramètre d’URL) / Basic / connexion auto ; ajoutée à chaque requête. Login refusé → exécution FAILED « Authentification : … », aucune étape jouée.
${authToken}Jeton obtenu par la connexion auto, injecté dans les variables de chaque VU (utilisable dans URL, en-têtes, corps).
Priorité des en-têtesUn en-tête défini par l’étape (comparaison insensible à la casse) remplace celui de l’application.
Capture de variableJsonPathExtractor : chemins à points ($.token, $.data.id), pas de tableaux ; variable propre à chaque VU.
Corps de réponseLu seulement si une assertion ou une capture est configurée (sinon ignoré pour économiser la mémoire).
Données collectéesPar requête : code HTTP, temps de réponse (ms), succès, erreur, horodatage ; puis métriques et statistiques.
Limites500 VU max par scénario (refus 400 à l’enregistrement) ; au lancement, 200 VU simultanés au total et 10 exécutions simultanées (refus HTTP 429). Valeurs configurables.
RobustesseAnnulation réelle (interruption des threads) ; au redémarrage, les exécutions orphelines passent en FAILED avec une raison.

7. Suppression et archivage

ÉlémentComportement réel
ÉtapeSuppression directe (SA, PE). Refusée si une exécution du scénario est QUEUED/RUNNING. Les résultats passés gardent leur copie (nom, méthode, URL) et step_id passe à NULL. Les étapes restantes sont renumérotées 1..n.
ScénarioImpact avant confirmation. Archiver (par défaut) : masqué des listes, non exécutable, planifications désactivées, restaurable. Supprimer définitivement (SA, saisie du nom) : métriques, résultats, exécutions, planifications, étapes et scénario supprimés dans une seule transaction.
ApplicationMême logique, cascade sur tous ses scénarios ; un scénario d’une application archivée est masqué et ne peut pas être restauré seul.
Exécution en coursToute suppression ou archivage est refusé : « Une exécution est en cours, arrêtez-la avant de supprimer. »
AuditActions DELETE, ARCHIVE et RESTORE tracées (succès et échec).

11. Limites et améliorations possibles

Constat (vérifié dans le code)Amélioration possible
Statut INACTIVE d’un scénario jamais attribué (aucun endpoint pour désactiver) ; le filtre « Inactif » est toujours vide. Le statut d’une étape n’est pas pris en compte par le moteur.Ajouter activer/désactiver, ou retirer ces statuts.
Page Scénarios : cases à cocher sans action groupée ; « tout sélectionner » prend toute la liste filtrée.Barre d’actions (archiver, exécuter) comme sur la page Applications.
Liste des scénarios et des étapes non paginée côté serveur (filtrage et pagination dans le navigateur) ; pas de sélecteur de tri.Pagination serveur comme /api/applications.
Aucun test frontend des pages Scénarios, Exécutions et de l’assistant.Tests Testing Library sur ces écrans.
Colonnes de clé étrangère sans index (sauf scheduled_execution).Migration ajoutant des index sur scenario_id, execution_id.
Une ligne de résultat et une métrique par requête (288 de chaque pour 20 s à 5 VU) : volume qui grossit vite.Agrégation par fenêtre de temps, rétention ou purge.
Générateur de charge dans la même JVM que l’API (limites 200 VU globaux, 10 exécutions).Workers d’injection séparés pour les fortes charges.
Connexion auto : un seul login par exécution, pas de renouvellement du jeton.Rafraîchissement du jeton pour les tests longs.
Capture JSONPath simplifiée (pas de tableaux ni filtres) ; corps de requête texte uniquement (pas de multipart).Bibliothèque JSONPath complète, support multipart.
Pas de montée/descente progressive en fin de test (ramp-down) ni de profils par paliers.Profils de charge à étapes.
Restaurer un élément archivé ne réactive pas ses planifications.Proposer la réactivation à la restauration.
Statistiques du rapport recalculées à chaque consultation depuis tous les résultats.Mise en cache du rapport d’une exécution terminée.
Bundle frontend de 678 kB (avertissement Vite > 500 kB).Découpage par route (import dynamique).
