Guide de présentation — PERFTEST / Cadence

Comprendre et présenter Cadence, page par page

Ce document explique, en français simple, ce que fait vraiment chaque page de Cadence — pas ce qu'elle est censée faire, ce qu'elle fait réellement dans le code. Il a été écrit après avoir lu le code source de chaque page (pas deviné), et après avoir réellement exécuté des scénarios contre un vrai serveur de test bancaire fictif.

Réel — vraies données, vraies requêtes HTTP Partiel — une partie réelle, une partie factice/locale Placeholder — écran "Bientôt disponible", rien derrière
Le concept central

Application → Server → Scenario → Steps → Execution → Metrics

C'est la chaîne que suit Cadence à chaque fois qu'on teste quelque chose. Chaque maillon est un vrai objet dans le code (un "type" TypeScript), pas juste une idée.

1 — La cible

Application

Le système qu'on veut tester : son URL, son type (Web/API), son authentification. Ex. le serveur bancaire fictif http://localhost:8000.

→
2 — La machine

Server (monitoring)

Le PC qui héberge l'application. Pas une page à part : c'est le champ monitoringUrl de l'Application qui pointe vers un petit service séparé donnant le vrai CPU/RAM.

→
3 — Le plan

Scenario

Le parcours de test : nom, application ciblée, nombre d'utilisateurs virtuels, montée en charge (ramp-up), planification.

→
4 — Les actions

Steps

Les requêtes HTTP une par une : méthode (GET/POST/PUT...), URL, headers, body, assertions à vérifier.

→
5 — L'action

Execution

Le vrai lancement du scénario : chaque étape envoie une vraie requête, pour chaque utilisateur virtuel.

→
6 — Le résultat

Metrics

Ce qu'on mesure après coup : temps de réponse, taux de succès, débit, CPU/RAM par étape.

Comment chaque maillon est représenté dans le code

Ce que je dis au Prof : "Le point important, c'est que rien n'est inventé — chaque nombre affiché (temps de réponse, taux de succès, CPU) vient d'une vraie requête HTTP envoyée par le navigateur. Si aucun serveur de monitoring n'est branché, on affiche null / un tiret, jamais une fausse valeur. Le seul maillon qui n'est pas une vraie ressource séparée en base, c'est 'Server' : c'est juste une URL de monitoring optionnelle sur l'Application, pas une page dédiée."

Détail page par page

Les pages principales

Le parcours naturel d'un utilisateur : se connecter, ajouter une application, créer un scénario, l'exécuter, en lire les résultats.

1. Login /login

src/pages/Login.tsx
Réel (démo)
Rôle

Écran de connexion. Sert à choisir qui utilise l'application (Admin / Testeur / Visiteur) — pas à vérifier un vrai mot de passe, car aucun serveur d'authentification n'est branché.

Fonctionnalités
  • RÉELLe formulaire valide vraiment l'email et le mot de passe (4 caractères min), et stocke la session (localStorage si "Se souvenir de moi" coché, sinon sessionStorage).
  • PARTIELN'importe quel email/mot de passe fonctionne — il n'y a pas de vraie base d'utilisateurs derrière (commenté dans le code : "Simulation d'authentification, aucun backend connecté").
  • RÉEL3 cartes "Admin / Testeur / Visiteur" pré-remplissent le formulaire pour changer de rôle en un clic — le rôle choisi contrôle ensuite canEdit partout dans l'app (le Visiteur ne peut rien modifier).
  • PLACEHOLDERLe lien "Mot de passe oublié" simule un envoi d'email mais n'en envoie aucun.
Exemple de test pratique
  1. Ouvrir la page Login.
  2. Cliquer sur la carte "Testeur" (pré-remplit le formulaire).
  3. Cliquer sur "Se connecter".
  4. Observer qu'on arrive sur le Dashboard, avec le badge de rôle "Testeur" en haut à droite.
Résultat attendu : connexion réussie, redirection automatique vers / (Dashboard).

Ce que je dis au Prof : "Il n'y a pas de vraie base de comptes — c'est volontaire pour cette maquette. Ce qui est réel, c'est la gestion du rôle : Admin/Testeur peuvent modifier des données, Visiteur est en lecture seule partout dans l'app."

2. Dashboard /

src/pages/Dashboard.tsx
Réel
Rôle

Vue d'ensemble : un coup d'œil sur la santé globale de la plateforme, avec possibilité de filtrer par application.

Fonctionnalités
  • RÉEL5 cartes KPI (temps de réponse moyen, débit, taux d'erreur, utilisateurs actifs, tests en cours) — 100% calculées à partir des vraies exécutions (aucun chiffre en dur, confirmé dans src/data/dashboardStats.ts).
  • RÉELGraphique "Évolution des temps de réponse" sur 7 jours — moyenne réelle par jour, 0 si aucune exécution ce jour-là (jamais une valeur inventée).
  • RÉEL"Exécutions récentes" et "Scénarios les plus utilisés" — cliquables, calculés sur les vraies exécutions.
  • RÉELSélecteur d'application en haut — recalcule toutes les statistiques pour une seule application.
Exemple de test pratique
  1. Depuis le Dashboard, choisir "Banking Test API" dans le sélecteur d'application.
  2. Observer que les 5 cartes KPI changent (elles ne comptent plus que les exécutions de cette application).
  3. Cliquer sur une ligne dans "Exécutions récentes".
Résultat attendu : redirection vers Exécutions, avec les chiffres du Dashboard qui correspondent exactement aux lignes du tableau.

Ce que je dis au Prof : "Ce tableau de bord ne contient aucune donnée factice — si je supprime toutes les exécutions, tous les chiffres retombent à zéro. C'est une vraie agrégation, pas un mock."

3. Applications /applications

src/pages/Applications.tsx
Réel
Rôle

Le carnet d'adresses des systèmes à tester. C'est la première chose à créer avant de faire un scénario — c'est le maillon "Application" de la chaîne.

Fonctionnalités
  • RÉEL"Tester l'application" envoie une vraie requête HTTP vers l'URL saisie (avec un délai maximum de 6 secondes) avant d'enregistrer — si le serveur ne répond pas, un vrai message d'erreur réseau s'affiche.
  • RÉELCréer/Modifier/Supprimer une application écrit vraiment dans la base (POST/PATCH/DELETE réels).
  • RÉELColonne "Statut" (Connectée/Non connectée) : déduite de la dernière exécution réelle, jamais une valeur au hasard.
  • RÉELColonnes "Scénarios" et "Dernière exécution" cliquables → navigation réelle.
  • PARTIELLe champ "URL de monitoring" (CPU/RAM) se remplit ici mais n'affiche rien sur cette page — il sert seulement plus tard, pendant une exécution (voir "Métriques").
Exemple de test pratique
  1. Cliquer sur "Ajouter une application".
  2. Nom : Banking Test API — URL : http://localhost:8000.
  3. Cliquer sur "Tester l'application".
  4. Attendre le message "Connecté".
  5. L'application est enregistrée automatiquement.
Résultat attendu : la ligne apparaît dans le tableau avec le statut Connectée (pilule verte).

Ce que je dis au Prof : "Le bouton Tester n'est pas décoratif : je peux le prouver en éteignant le serveur bancaire — le message d'erreur change immédiatement en un vrai message réseau (connexion refusée)."

4. Scénarios /scenarios

src/pages/Scenarios.tsx
Réel
Rôle

La liste de tous les parcours de test créés, avec un aperçu direct de leurs étapes, et le bouton pour les lancer.

Fonctionnalités
  • RÉELSous le nom de chaque scénario : l'aperçu réel de ses étapes dans l'ordre (ex. 1. POST /api/auth/login → 2. GET /api/account/balance).
  • RÉELBouton ▶ "Exécuter le scénario" — ouvre une vraie modale de lancement (VUs, ramp-up), puis envoie de vraies requêtes HTTP.
  • RÉEL"Détail exécution" — lien direct vers la dernière exécution réelle de ce scénario.
  • RÉELModifier/Supprimer/Dupliquer un scénario — actions réelles sur la base.
Exemple de test pratique
  1. Repérer le scénario "Transfert national".
  2. Vérifier que l'aperçu sous le nom montre bien ses 2 étapes (login + virement).
  3. Cliquer sur ▶ "Exécuter le scénario".
Résultat attendu : la modale "Configurer le test" s'ouvre avec l'application et le scénario déjà présélectionnés.

Ce que je dis au Prof : "Avant, cette ligne affichait juste un identifiant technique (#SCN-1) sans intérêt. Je l'ai remplacée par les vraies étapes du scénario, pour qu'on comprenne ce qu'un scénario va faire sans devoir l'ouvrir."

Étape 0 de la création : choisir d'abord l'application à tester, puis soit partir d'un scénario prêt à l'emploi, soit créer le sien de zéro.

Exemple de test pratique

  3. Sur la carte "Transfert international", cliquer "Utiliser ce scénario".
Résultat attendu : redirection automatique vers l'écran "Étapes" du scénario, déjà rempli avec 2 étapes (login + transfert international).

Ce que je dis au Prof : "Ces scénarios recommandés ne sont pas juste des exemples affichés à l'écran : cliquer dessus crée un vrai scénario en base avec ses vraies étapes, immédiatement modifiable."

6. Créer / Modifier un scénario — Étapes /scenarios/create

src/pages/CreateScenario.tsx
Réel
Rôle

Le cœur de la construction d'un scénario : donner un nom, choisir l'application, et lister ses étapes dans l'ordre.

Fonctionnalités
  • RÉELChamp "Nom du scénario" modifiable.
  • RÉELChamp "Application" grisé et verrouillé une fois choisi — impossible de le changer par erreur après coup (icône cadenas).
  • RÉELTableau des étapes : numéro d'ordre, méthode HTTP (GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS/TRACE), nom, URL, statut (Actif/Inactif) — tout réel, sauvegardé au fur et à mesure.
  • RÉELRéordonner les étapes (flèches haut/bas), les supprimer, les activer/désactiver, "Tester" le scénario en direct (vraies requêtes) avant de l'enregistrer pour de bon.
Exemple de test pratique
  1. Cliquer "+ Ajouter une étape".
  2. Méthode : GET, Nom : "Consulter le solde", URL : /api/account/balance.
  3. Cliquer sur "Tester" en bas de page.
Résultat attendu : une fenêtre affiche le vrai résultat de la requête (code HTTP, temps de réponse) sans quitter la page.

Ce que je dis au Prof : "J'ai bloqué le champ Application une fois choisi — c'est une vraie contrainte métier : un scénario appartient à une seule application, pour toujours. Le changer par erreur casserait le lien avec les étapes déjà configurées."

7. Configuration d'étape /scenarios/create-step

src/pages/CreateStep.tsx (5 écrans internes)
Réel
Rôle

Le détail fin d'une étape (headers, body, assertions) puis, plus loin dans le même assistant, les réglages globaux du scénario : Utilisateurs virtuels et Planification, avant le Résumé final.

Fonctionnalités
  • RÉELConfiguration complète d'une étape : headers HTTP, body JSON, assertions (ex. "Status code = 200"), Think Time / Pacing, timeout, follow redirects.
  • RÉELÉcran "Utilisateurs" : nombre d'utilisateurs virtuels, ramp-up (montée en charge progressive), source de données (manuel ou CSV).
  • RÉELÉcran "Planification" : Immédiate (lance le scénario dès l'enregistrement), Planifiée (à une date/heure précise), Récurrente (se relance seule selon une fréquence).
  • RÉEL"Tester cette étape" : vraie requête HTTP isolée, avec vraies assertions évaluées contre la vraie réponse.
Exemple de test pratique
  1. Sur l'étape "Consulter le solde", ajouter un header Authorization: Bearer TEST-TOKEN-123.
  2. Cliquer "Tester cette étape".
  3. Avancer jusqu'à "Planification" et choisir "Immédiate".
  4. Cliquer "Enregistrer le scénario".
Résultat attendu : le test isolé renvoie 200 OK avec le vrai solde ; après l'enregistrement, une exécution démarre automatiquement (sans clic supplémentaire).

Ce que je dis au Prof : "'Immédiate' et 'Récurrente' ne sont pas juste des libellés : Immédiate lance vraiment le scénario à l'enregistrement, et Récurrente se replanifie toute seule (quotidien/hebdomadaire/mensuel) après chaque déclenchement — je l'ai vérifié en la laissant tourner : une deuxième exécution s'est lancée automatiquement."

8. Exécutions /executions

src/pages/Executions.tsx
Réel
Rôle

La liste de tous les tests lancés, avec leur statut, pour suivre ce qui tourne et ce qui vient de se terminer.

Fonctionnalités
  • RÉELColonnes : #, Scénario, Application, Statut, Utilisateurs, Durée, Démarré le, Actions — toutes réelles.
  • RÉELSous le nom du scénario : chaque étape avec son résultat coloré — 1. POST /login (Réussi) → 2. GET /balance (Réussi).
  • RÉELOnglets de filtre (Toutes/En cours/Réussies/Avec erreurs/Échouées) et recherche — filtrage réel.
  • RÉEL"Suspendre"/"Arrêter" une exécution en cours — action réelle sur la base.
  • RÉEL👁 "Voir les détails" et 📄 "Voir le rapport" — deux vues différentes de la même exécution réelle.
Exemple de test pratique
  1. Lancer un scénario avec 2 utilisateurs virtuels.
  2. Pendant l'exécution, cliquer "Annuler" dans la fenêtre de progression.
Résultat attendu : l'exécution s'arrête quasi instantanément (moins de 2 secondes) et passe au statut "Annulée" — même si un ramp-up de 60 secondes était configuré.

Ce que je dis au Prof : "J'ai corrigé un vrai bug ici : avant, Annuler pouvait mettre jusqu'à une minute à s'arrêter parce que les pauses entre requêtes n'étaient pas interruptibles. Maintenant elles le sont — je peux le démontrer en direct avec un ramp-up long."

9. Détail d'exécution /executions/detail/:id

src/pages/ExecutionDetail.tsx
Réel
Rôle

Le résultat complet d'UNE exécution précise : chaque étape, chaque code HTTP, chaque cause d'échec.

Fonctionnalités
  • RÉELBandeau de résumé : statut global du scénario + nombre d'étapes réussies + nombre d'étapes échouées, en un coup d'œil.
  • RÉEL9 indicateurs de performance (durée, VUs, requêtes, taux de réussite/erreur, moyenne/min/max, débit) — calculés sur les vraies réponses HTTP.
  • RÉELChronologie, graphiques (temps de réponse, taux de réussite), et tableau "Résultat de chaque étape" avec code HTTP, ✅/❌, et le corps réel de la requête/réponse dépliable.
  • RÉELEn cas d'échec : la vraie cause est affichée (ex. HTTP 401: Identifiants invalides).
  • RÉELFiltre par utilisateur virtuel (VU 1, VU 2...) quand plusieurs VUs ont tourné.
Exemple de test pratique
  1. Ouvrir le détail d'une exécution qui a échoué.
  2. Dérouler "Réponse" sur l'étape en échec.
Résultat attendu : le vrai code HTTP (ex. 401 ou 404) et le vrai message d'erreur renvoyé par le serveur sont visibles, pas un message générique.

Ce que je dis au Prof : "Le bandeau en haut ('3 étapes réussies, 1 échouée') est nouveau — avant il fallait compter soi-même dans le tableau. Maintenant le statut global saute aux yeux immédiatement."

11. Métriques /metriques

src/pages/Metriques.tsx
Réel
Rôle

L'écran d'analyse le plus poussé : on descend de "toutes les applications" jusqu'à une seule étape précise, avec le CPU/RAM serveur si disponible.

Fonctionnalités
  • RÉEL3 sélecteurs en cascade : Application → Scénario → Étape, chacun recalculant tous les indicateurs et graphiques.
  • RÉEL"Top Applications", "Top Scénarios", "Top Erreurs" — classements réels basés sur les vraies exécutions.
  • RÉELAu niveau "Étape" : bloc "Consommation serveur" — CPU/RAM moyens réels, ou message explicite si aucun monitoring n'était branché ("Aucun relevé CPU/RAM pour cette étape").

Exemple de test pratique

  2. Regarder le bloc "Consommation serveur".
Résultat attendu : si aucune URL de monitoring n'est configurée sur l'application, le bloc affiche honnêtement l'absence de donnée — pas un chiffre inventé.

Ce que je dis au Prof : "C'est ici que se referme la boucle CPU/RAM : la valeur vient de l'URL de monitoring saisie sur la page Applications, capturée pendant l'exécution, puis moyennée ici par étape."

7 tests, de A à Z

Une suite complète, dans l'ordre logique, pour prouver que chaque brique fonctionne réellement.

Test 1 — Ajouter une application

Réel
Précondition

Être connecté, page Applications ouverte.

Actions
  1. Cliquer "Ajouter une application".
  2. Nom : Banking Test API.
  3. URL : http://localhost:8000.
  4. Cliquer "Tester l'application".
Résultat attendu : message "Connecté", application créée avec le statut Connectée affiché dans le tableau.

Test 2 — Créer un scénario

Réel
Précondition

Application "Banking Test API" créée (Test 1).

Actions
  1. Aller sur Scénarios → Nouveau scénario.
  2. Choisir "Banking Test API".
  3. Sur "Consultation solde et commission", cliquer "Utiliser ce scénario".
Résultat attendu : redirection vers l'écran Étapes, scénario nommé "Consultation solde et commission" avec 2 étapes déjà présentes.

Test 3 — Ajouter des étapes manuellement

Réel
Précondition

Un scénario ouvert en édition.

Actions
  1. Cliquer "+ Ajouter une étape".
  2. Méthode GET, Nom "Historique", URL /api/agent/history.
  3. Valider — la nouvelle étape apparaît en bas du tableau.
  4. Utiliser la flèche ↑ pour la remonter en 1ère position.
Résultat attendu : le tableau affiche bien 3 étapes dans le nouvel ordre choisi.

Test 4 — Exécuter un scénario

Réel
Précondition

Le serveur bancaire de test (banking-test-api) est démarré.

Actions
  1. Depuis Scénarios, cliquer ▶ "Exécuter le scénario".
  2. Laisser les valeurs par défaut, cliquer "Suivant" puis "Lancer".
  3. Attendre la fin (quelques secondes).
Résultat attendu : toast "Exécution terminée avec succès", nouvelle ligne visible dans Exécutions avec le statut Réussie.

Test 5 — Consulter les métriques

Réel
Précondition

Au moins une exécution terminée (Test 4).

Actions
  1. Aller sur Métriques.
  2. Choisir "Banking Test API" dans le premier sélecteur.
  3. Choisir le scénario testé, puis une étape.
Résultat attendu : les graphiques et le tableau se mettent à jour avec les vraies mesures de cette étape (temps de réponse, taux de réussite).

Test 6 — Vérifier le Server Snapshot (CPU/RAM)

Réel si monitoring branché
Précondition

Le service local-monitoring-server est démarré (npm run monitor).

Actions
  1. Sur Applications, modifier "Banking Test API", renseigner l'URL de monitoring http://localhost:5000/server-metrics.
  2. Relancer une exécution (Test 4).
  3. Aller sur Métriques → niveau Étape → bloc "Consommation serveur".
Résultat attendu : CPU/RAM réels de la machine affichés — et si le service de monitoring n'est pas lancé, un message explicite ("aucun relevé") au lieu d'un chiffre inventé.

Test 7 — Consulter l'historique des exécutions

Réel
Précondition

Plusieurs exécutions déjà lancées.

Actions
  1. Aller sur Exécutions (le menu "Historique" est un placeholder — utiliser celui-ci, c'est le vrai historique).
  2. Filtrer sur l'onglet "Réussies".
  3. Ouvrir le détail d'une exécution.
Résultat attendu : liste filtrée correctement, détail complet avec chaque étape et son statut réel.
